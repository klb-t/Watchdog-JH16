# Field and clinical interfaces

**Epic E6. Coarse by design, like E2–E5 — decomposed into tasks when its turn comes. Nothing
here is built before E1 exits; only the schema in `02_DATA_MODEL.md` exists early, per D12.**

## Scope, and how it differs from E1

E1 answers a population-level question: does a search-count signal track substance popularity
and harm across a sixteen-substance set, the way JH2016 found. E6 answers an individual-case
question: a specific person, in front of a specific responder, right now — what is known about
what they may have taken, and what should the responder do next.

These are different system classes with different failure costs. A wrong `Hi` value in E1
produces a wrong data point in an aggregate chart. A wrong pill identification in E6 can
contribute to a wrong clinical decision about one real person. Nothing in E6 relaxes any
contract from `03_JH2016_CONTRACT.md` or `04_METHOD_COMPILER_AND_APPROVAL.md`; if anything, E6
applies them more strictly, because the stakes are higher, not because a new set of rules is
needed.

This scope split, and the sequencing that follows from it, is not new: the maintainer's own
April 2026 prioritisation already marked responder tooling "confirmed, post-MVP" while
researcher tooling was "priority MVP." E6 formalises that ordering; it does not invent it.

## Hard constraint: retrieval over curated sources, never generated clinical content

This is the same rule as `03_JH2016_CONTRACT.md`'s "no LLM in the numerical path," restated for
this domain because the temptation to violate it is stronger here.

- Every clinical fact shown on a card — a dose range, an interaction, a contraindication, a
  poisoning symptom — is retrieved from a versioned, sourced, citable reference, exactly like
  `reference_scores` already is for Nutt et al. 2010. It is never generated by a language model
  from general knowledge, and never phrased by a model in a way that could be read as a
  recommendation.
- A language model may help a responder *search* — parsing free-text symptom entry into the
  symptom ontology, ranking candidate pill matches — but it never originates the clinical
  content itself, and every model-touched result is `PROPOSED` until a human curator has
  approved the underlying source mapping, per `04_METHOD_COMPILER_AND_APPROVAL.md`.
- The system never recommends a treatment or a dose. It surfaces what curated sources say and
  links to them. Treatment decisions remain the clinician's, against actual protocol.
- Every card carries a visible, unmissable statement that this is not a diagnosis and does not
  replace emergency services or poison control, plus the escalation block below. This is not
  boilerplate to be shrunk in a later design pass — it is a permanent, non-collapsible element
  of the layout.

## Symptom search

Two entry paths into the same symptom ontology (`02_DATA_MODEL.md` §Field reference):

**Checklist** — symptoms grouped by body system (neurologic, cardiac, respiratory, dermatologic,
psychiatric, gastrointestinal), tappable, zero typing required. This is the fast path and the
default for the responder card.

**Free text** — the maintainer's own worked example typed the query as observed symptoms plus
context in one line, not a structured form. Free text is parsed into symptom-ontology
candidates through the *same* `extraction_candidates` / `verification_state` promotion path
already specified for the community-report pipeline — a different call site on an existing
mechanism, not a new one.

A search returns a **ranked list of candidate substances, never a single verdict.** Matching is
a deterministic score over `assertions` filtered to `predicate IN (ASSOCIATED_WITH_SYMPTOM,
ASSOCIATED_WITH_EFFECT, ASSOCIATED_WITH_TOXICITY)` (`12_DRUG_DOMAIN_ONTOLOGY_AND_ASSERTIONS.md`)
— a weighted overlap or a curated base-rate calculation — never an LLM-assigned probability;
`04_METHOD_COMPILER_AND_APPROVAL.md`'s "no LLM in the numerical path" applies here without
modification. Each candidate shows its supporting assertions with their individual evidence
tiers, so a responder can see *why* a substance was suggested, not just that it was.

## Pill and sample identification

Search fields, matching the maintainer's own specification: description, colour, shape, logo,
**score line** (the break-line pressed into a pill — an identification feature easy to omit and
worth keeping), or direct substance name if already suspected.

A photo may be submitted in addition to structured fields. Matching against `pill_types`
returns ranked candidates with their composition, each composition row tagged with its
`evidence_tier` per `10_EVIDENCE_TIER_AND_TRUST_UI.md`.

**The ceiling that matters most in this entire epic:** composition inferred from visual
matching alone is capped at `MODELED_PREDICTED`, never higher, regardless of match confidence.
Counterfeit pills exist specifically to look like something they are not — visual similarity is
adversarial against exactly the highest-risk case, a pill pressed to resemble a known-safer
substance while actually containing something else. A high-confidence visual match displayed
with the same visual weight as a lab result would be actively dangerous, not merely imprecise.
For any match not backed by a `tested_samples` row, the card's primary call to action is
locating a drug-checking service, not the identification itself.

**Adulterant and look-alike warnings** — a `pill_types` entry accumulates known hazards over
time as `batch_alert_rules` fire `batch_alerts` of type `adulterant_detected` or
`look_alike_warning` against it. These render as a prominent banner on the card, separate from
and above the evidence-tier badge cluster, because an active warning is time-sensitive
situational information, not a background trust signal.

## Search by market label — "what's commonly sold as X"

The concrete requirement this section exists to satisfy: search by what a substance is
commonly sold or represented as — the maintainer's own example was amphetamine — and get back,
easily, the interactions of whatever it actually turns out to contain. Mechanism, predicate
vocabulary and the full acceptance query are specified once in
`12_DRUG_DOMAIN_ONTOLOGY_AND_ASSERTIONS.md` §Market labels; this section states only what the
UI does with it.

A search resolves the term against `market_labels`' `canonical_label_group` under an explicit
query-expansion mode (`STRICT_CANONICAL` would not find "speed" for "amphetamine" — this search
by construction runs at `LOCALIZED_SYNONYMS` or wider, and that mode is shown, not hidden). The
result is not one substance — it is a ranked distribution of what has actually been found under
that label, in the selected region and time window, each entry showing:

- the actual substance(s) found, ranked by frequency in the sample set within region/time
- the fraction of samples where the actual finding diverged from the claimed label — the
  misrepresentation rate is exactly the point of the query and is never buried
- for each actual substance, its known interactions (`INTERACTS_WITH` assertions), each with
  its own citation and evidence tier
- the graph path for every result — label → sample(s) → composition → substance → interaction —
  so a researcher or responder can see why a result appeared, not just that it did
- any contradiction between sources, shown rather than silently resolved

"Counterfeit" is never applied on the strength of a visual mismatch alone — it is an
evidence-backed classification, requiring a `TESTED_AS`/`CONTAINS` assertion that actually
disagrees with the claimed label, per `12_DRUG_DOMAIN_ONTOLOGY_AND_ASSERTIONS.md`.

## Responder card layout

Renders the fixed twelve-category content order from
`12_DRUG_DOMAIN_ONTOLOGY_AND_ASSERTIONS.md` §Substance profile projection. Each fact within a
section carries its own evidence-tier badge; sections are not colour-coded as a whole.

The pharmacodynamics section reads from `assertions` filtered to
`predicate IN (BINDS_TO, AGONIST_AT, ANTAGONIST_AT, MODULATES, INHIBITS, INDUCES)` with
`object_type = target`; a "chemistry and structural relations" line reads the same table
filtered to `ANALOG_OF`/`STRUCTURALLY_SIMILAR_TO`/`METABOLITE_OF` between two substances.
Neither section is a free-text field a model fills in — both are graph queries over sourced,
cited rows, same as everything else in this epic.

Above all content, always visible, never scrolled past:

- any active `batch_alert` for the matched pill type or substance
- the not-a-diagnosis statement
- the escalation block: regional emergency number and poison-control contact, resolved from a
  configuration table keyed by geography (`00_STATE_AND_DECISIONS.md` Q6) — **never hardcoded**,
  and never populated from a model's general knowledge of what a country's emergency number is.
  Verify any seeded contact against a current official source before shipping it, not from
  training data.

## Offline mode

A responder in the field may have no connectivity. The card must work fully from a local,
previously synced subset of the reference data — same principle as D2's SQLite-first
architecture, extended to this epic rather than reinvented for it: the offline responder card is
what D2 was for all along, not a new requirement bolted on later.

Sync is one-directional and scheduled: pull reference data and approved alert rules when
connected, cache locally, serve entirely from cache when not. A stale-cache indicator states
how old the local data is — a responder should know if they are looking at reference data from
three weeks ago, not just accept a card as current implicitly.

## Source seed list

Not a closed list, and not permission to implement all of it at once — the same convention as
`05_PROVIDERS_AND_CAPABILITIES.md`. Everything here starts `status: planned`. Most of these have
no public API and begin as manual, versioned import (reusing the E5 dataset-import path) rather
than live fetch.

**Pill testing / drug checking** — DIMS, the Dutch national drugs-information-and-monitoring
network (Trimbos-coordinated; Jellinek, Unity and regional GGD services are operational
instances, confirmed active as of this writing), DrugsData/EcstasyData, PillReports.

**Toxicology and early warning** — EMCDDA Early Warning System, UNODC SMART/NPS database,
forensic toxicology references (TIAFT, SWGDRUG).

**Pharmacology** — BindingDB, IUPHAR/Guide to Pharmacology, PubChem BioAssay.

**Structural and computed chemistry** — PubChem CID, ChemSpider, OPSIN, RDKit for structure;
AdmetSAR, pkCSM, SwissADME for ADMET prediction. Predicted values from this group are
`MODELED_PREDICTED` by construction, never promoted regardless of how the tool presents its own
confidence.

**Reference/encyclopedic** — Wikipedia, DrugBank, PsychonautWiki — the last explicitly
lower-control per the maintainer's own prior notes; tag accordingly, do not average it in with
regulatory sources at ingestion.

Community sources (Erowid, TripSit) feed `RAW_OBSERVATIONAL` field-signal content only; they
never populate PK/PD/toxicity sections directly.

## Privacy and audit

Every lookup generates a standard `audit_events` row, per `02_DATA_MODEL.md`, at higher
importance here than elsewhere in the system: a life-safety tool that cannot show who searched
what, and when, has a real accountability gap if something goes wrong.

Set against that: the field interface **never accepts a patient-identifying field** — no name,
no date of birth, no case number that could be traced to a specific person outside this system.
This is a deliberate scope limit, not an oversight, and it sidesteps a category of compliance
burden this project has no infrastructure for yet. If a future version needs case-linkage, that
is a new decision requiring the same scrutiny D3 gave authentication, not a quiet field addition
to this epic.

Retention and who may review a responder's own lookup history is `00_STATE_AND_DECISIONS.md` Q5,
open until E4 gives this project real roles to grant.

## Required tests

| Test | Asserts |
|---|---|
| no clinical generation | no code path in this epic passes model output directly to a card field typed as clinical content without a source citation attached |
| symptom search returns candidates, not a verdict | a symptom query never returns a single substance with no alternatives shown |
| pill match ceiling | enforced in the domain layer per `10_EVIDENCE_TIER_AND_TRUST_UI.md`, re-asserted here at the search-endpoint level |
| escalation block always present | no card renders, in any state including error and loading, without the not-a-diagnosis statement and a resolved or explicitly-empty escalation contact |
| no patient-identifying input | the search API rejects or strips any field matching a name/DOB/case-number pattern |
| offline completeness | a full responder-card session — symptom search, pill search, card render, alert display — completes with the network disabled, against synced fixtures |
| stale-cache disclosure | a card sourced from data older than the configured sync threshold visibly states its cache age |
| alert rule reuse of approval gate | a `batch_alert_rules` row is unusable to produce a `batch_alerts` firing while `PROPOSED`, identically to a method spec |
| market-label lookup returns a distribution, not a verdict | a query against a `canonical_label_group` returns ranked actual-substance candidates with frequency, never collapses to one answer |
| counterfeit requires evidence | no UI surface applies a "counterfeit" or equivalent label from a visual mismatch alone, absent a `TESTED_AS`/`CONTAINS` assertion contradicting the claimed label |

The full knowledge-graph acceptance suite (KG-1 through KG-5, including the amphetamine
regional-lookup end-to-end test) is specified once in `09_TESTS.md` rather than duplicated here.
