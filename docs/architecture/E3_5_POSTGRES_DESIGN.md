# E3.5 — PostgreSQL as a durable backend: design and first package

Status, 2026-10-26: **design + first package**. PostgreSQL is **not** a working backend yet.
The owner's VM stays on SQLite on its local persistent disk until he decides otherwise.

## Why

The Cloud Run half of E3.5 is reopened (ledger, "OPEN — E3.5"). SQLite on GCS FUSE does not satisfy the
database contract. A VM with SQLite on a local persistent disk is a valid arrangement, and it is the
current one. A managed transactional database is needed only for Cloud Run, more than one instance, or
managed point-in-time recovery.

## What exists today (measured on `b98fe36`)

| Item | Count |
|---|---|
| Migrations (raw SQLite SQL, `db/migrations/`) | 25 (1395 lines) |
| Tables / triggers after all migrations (SQLite) | 103 (incl. `schema_migrations`) / 51 |
| Repository files (`db/repositories/`) | 24 |
| Synchronous `prepare()` calls outside migrations | 337 in 21 files |
| Drizzle synchronous calls (`.all()/.get()/.run()`) | about 50 |
| `transaction(...)` uses / immediate transactions | 59 / 14 |
| `INSERT OR IGNORE` / `INSERT OR REPLACE` | 41 total |
| WORM triggers via `RAISE(ABORT, …)` | 51 |
| Drizzle schema | `sqlite-core` only |

The hard part is not the schema. It is that **every repository, and every caller up to the route
handlers, is synchronous** (better-sqlite3). The `pg` driver is asynchronous. A PostgreSQL backend
therefore means changing every repository method to return a Promise, and `await` through services and
routes. Transactions that now rely on SQLite's single writer, such as the admission grant rechecks
(E4.7) and the immediate transactions, need explicit isolation (`SERIALIZABLE` with retry, or
`SELECT … FOR UPDATE`) and their own tests.

## First package (this change)

1. `backend/watchdog_api/db/postgres_dialect.ts`: a mechanical SQLite → PostgreSQL translation of the
   migrations. The rules are explicit in the code:
   - trigger `RAISE(ABORT,'m')` → a plpgsql function plus a `FOR EACH ROW` trigger, with `UPDATE OF cols`
     and the message kept;
   - a `WHEN` containing a subquery (not allowed in PostgreSQL) → a guard in the function body;
   - `INTEGER PRIMARY KEY AUTOINCREMENT` → `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`;
   - `BLOB` → `BYTEA`;
   - `STRICT` → dropped;
   - `json_valid(c)` → a `c::jsonb` check;
   - `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING`;
   - `datetime('now')` → `now()` formatted as before.

   `INSERT OR REPLACE`, or any trigger body other than one `RAISE(ABORT)`, is reported as a manual
   step, never guessed. None exist in the 25 migrations.
2. `scripts/pg_portability_probe.ts`: applies all translated migrations to a real PostgreSQL server
   inside one transaction, then rolls back. It checks that a ported WORM trigger refuses an `UPDATE`.
3. The `WATCHDOG_DB_BACKEND` setting (`db/backend_setting.ts`):
   - `sqlite` (default) works;
   - `postgres` stops startup with `NotImplementedError`;
   - any other value is an error.

   Nothing silently falls back to SQLite.
4. Tests: `tests/unit/postgres_dialect.test.ts` (offline). It checks that every shipped migration
   translates with no manual step and keeps all 51 triggers, plus the individual rules and the setting.

### Probe result (real server)

Run on 2026-10-26 against `postgres:16-alpine` (PostgreSQL 16.15) in a disposable local container.
Evidence: `docs/history/evidence/2026-10-26-e3-5/pg_probe.json`.

| | Result |
|---|---|
| Migrations | 25 / 25 applied |
| Source statements → PostgreSQL statements | 235 → 286 |
| Failed / manual | 0 / 0 |
| Tables / triggers | 102 (SQLite 103 incl. `schema_migrations`, which the probe does not create) / 51 |
| WORM check | `UPDATE study_protocols` refused: "WORM study protocol" |

The first two probe runs failed: 280, then 28 failures. That exposed two real translation problems,
which are now covered by tests:
- comments containing `;` or `'` split statements;
- PostgreSQL refuses a subquery in a trigger `WHEN`. This affected 3 triggers in migration 016.

### What the probe does **not** show

- Type semantics. Booleans stay `INTEGER 0/1` and timestamps stay ISO `TEXT`. That keeps
  repository code unchanged, but it is not idiomatic PostgreSQL. Comparisons and sorting on these
  columns behave the same, because the text is ISO 8601.
- The moved-guard triggers (016) were created, but not exercised with data.
- No repository query has run against PostgreSQL. Differences remain in `GROUP BY` strictness,
  `LIKE` case sensitivity, integer division, `||` on NULL, and the `lastInsertRowid` pattern.
- Concurrency and isolation, backup/restore (`pg_dump` versus the E3.15 archive format), and
  migration from an existing SQLite file are not covered.

## Options for the owner's decision

| Option | What it is | Cost | Gives |
|---|---|---|---|
| **A. Stay on SQLite on the VM** (current) | local persistent disk + verified E3.15 backup | 0 | durable single instance; no Cloud Run |
| **B. SQLite + continuous replication** (Litestream to GCS) | WAL streamed to a bucket | small | point-in-time restore of the VM; still single writer, still no Cloud Run |
| **C. PostgreSQL backend** (Cloud SQL or a self-managed instance) | async repository port, phased | large (all 24 repositories, services, routes) + monthly database cost | Cloud Run / several instances, managed PITR |

**Recommendation:**
- Keep A now. B is the cheapest real gain in durability, if the owner wants restores finer than the
  E3.15 archives.
- Start C only when Cloud Run or more than one instance is actually wanted. The phases are below.

A Cloud SQL instance is paid spending, and needs the owner's yes.

## Phased plan for C (each phase is its own PR with tests)

1. **Async repository interface.** Make the repository methods `async` while staying on SQLite. This
   changes behaviour nowhere, and the full gate must stay green. It is the largest diff, and it is
   mechanical.
2. **Backend-neutral SQL.** Replace `INSERT OR IGNORE`/`REPLACE`, `lastInsertRowid` and SQLite
   functions in repository queries with forms both engines accept, or with dialect helpers.
3. **PostgreSQL adapter.** `pg` pool, migrations through `postgres_dialect`, a `schema_migrations`
   table, explicit isolation for the 14 immediate transactions, and retry on serialization failure.
4. **Dual-backend test gate.** CI runs the integration tests on SQLite and on a PostgreSQL service
   container. `WATCHDOG_DB_BACKEND=postgres` is enabled only after this passes.
5. **Data migration and recovery.** Copy an SQLite database into PostgreSQL and verify row counts and
   content hashes. `pg_dump` joins the backup archive, and a restore drill is run.
6. **Cloud Run.** Only after 1–5, with a transaction, replacement and recovery test on the real
   deployment, as the ledger requires.

## How to re-run the probe

```bash
docker run -d --name wd-pg-probe -e POSTGRES_PASSWORD=... -e POSTGRES_DB=watchdog_probe -p 127.0.0.1:55432:5432 postgres:16-alpine
PGURL=postgres://postgres:...@127.0.0.1:55432/watchdog_probe npx tsx scripts/pg_portability_probe.ts > probe.json
docker rm -f wd-pg-probe
```

The probe rolls back its transaction, so the database is left empty.
